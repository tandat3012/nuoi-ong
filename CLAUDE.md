# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.
For unfamiliar features, don't build from scratch. First search GitHub for open-source projects to compare ideas before starting work.

Nuôi Ong is a beekeeping farm back office (equipment, materials, warehouses, inventory, assets, maintenance, personnel) plus a public storefront ("Mộc Ong"). `web/` is Next.js 16 / React 19 / Tailwind 4; `api/` is NestJS 11 + Drizzle ORM + PostgreSQL; `mobile/` is an Expo 57 / React Native app for staff (see `mobile/README.md`); Clerk handles auth. User-facing text is Vietnamese.

## Rules from project files

- Use Graphify skill that have already installed to explore what you need for that module or project
- Before any Git action (branch, commit, pull, push, PR, release, hotfix), read and follow `GIT_WORKFLOW.md`: branch `feature/*`/`fix/*` from `dev`, PR into `dev`; `main` only takes merges from `dev`; no direct pushes to either.
- Do not add or commit `.md` or `.docx` files without asking (`web/AGENTS.md`).
- `web/` runs a Next.js version with breaking changes from older releases: read the relevant guide in `web/node_modules/next/dist/docs/` before writing Next.js code. The block in `web/AGENTS.md` is regenerated by `next dev`; leave it in place.

## Commands

`web/`, `api/` and `mobile/` are independent pnpm projects (own lockfile and workspace file; `mobile/` uses `nodeLinker: hoisted`); run commands inside the app directory. In `mobile/`: `node node_modules/typescript/bin/tsc --noEmit`, `node node_modules/jest/bin/jest.js`, `CI=1 node node_modules/expo/bin/cli export --platform android`. The repo-root `Makefile` wraps the common ones (`make fe`, `make be`, `make db-up`, `make db-migrate`, `make db-seed`, `make db-reset`). `docker compose up --build` runs web :3000, API :5050 and PostgreSQL on host port 5435.

On this machine `pnpm exec …` can fail with "Exec format error"; call the tool binaries directly (`npx tsc` works):


### Test databases

- `test/*.integration.e2e-spec.ts` suites run against `DATABASE_URL` from `api/.env` (local dev DB `localhost:5435/nuoi_ong`). Most create their own fixtures, but some assertions can be thrown off by existing dev rows.
- `storefront-seed` and `storefront-schema` suites refuse to run unless the DB name contains `test`. They always fail against the dev DB; that is expected.
- `pnpm test:assets` (asset + stock document suites) requires `TEST_DATABASE_URL` on localhost with a DB name ending in `_test`, migrated first: `DATABASE_URL="$TEST_DATABASE_URL" pnpm db:migrate`.
- `pnpm test:db` (`test/jest-db.json`) runs only the database, commerce/store-admin/store-orders integration and storefront schema/seed suites.

Swagger is served only when `NODE_ENV=development`: `http://localhost:5050/api/v1/docs`. Its "Try it out" calls the real API.

## Architecture

### API request pipeline (`api/src`)

- All routes are under `/api/v1`. A global `ValidationPipe` transforms DTOs and rejects unknown properties.
- `ClerkAuthGuard` is global; opt out with `@Public()` (health, root, public `/store` catalog reads). `AccountStateGuard` blocks accounts flagged `must_change_password` unless the handler has `@AllowInitialPassword()`.
- Farm-scoped endpoints take `farmId` as a query parameter and use `FarmAccessGuard` + `@FarmRoles(...)` (roles: `ADMIN`, `FARM_OWNER`, `EMPLOYEE`, `GUEST`). Membership is checked per farm; there is no system-role bypass.
- Controllers stay thin; services use `DatabaseService` (typed Drizzle over a `pg` pool). Shared query parsing and Swagger decorators live in `src/common/` (`parsePagination`, `requireUuid`, `ApiFarmIdQuery`, …).
- The Drizzle schema in `src/db/schema/` (`schema.ts` for the farm and warehouse domain, `storefront.ts` for the store, `relation.ts`) is the source of truth. `drizzle/` holds generated migrations and their meta journal; never hand-edit the snapshots.

### Stock is moved only by confirmed documents

- Receipts, issues, transfers and counts (`modules/warehouses/`, one controller/service per document) and inventory adjustments (`modules/inventory/`) all follow DRAFT → confirm or cancel.
- Stock documents also have an approval step: DRAFT → submit → PENDING_APPROVAL → confirm, or reject with a reason → REJECTED (final). ADMIN/FARM_OWNER are approvers and may confirm a DRAFT directly; EMPLOYEE edits, cancels and submits only their own drafts; GUEST cannot create. Submit notifies approvers, confirm/reject notify the creator, and every action writes an audit log in the same transaction.
- Employees file `maintenance-requests` and `asset-transfer-requests` (one pending per asset; a pending transfer holds the asset in `TRANSFER_PENDING`); approval runs the real maintenance scheduling or asset transfer in the same transaction.
- Every QR is a web URL: `/scan/{assetCode}`, `/scan/item/{itemId}`, `/scan/inventory/{balanceId}` (`api/src/common/qr.ts`).
- Balances and the inventory ledger change only inside the confirm transaction. Services lock rows with `.for('update')` and re-check state, so concurrent confirms are safe.
- Items have a tracking mode: `QUANTITY`, `LOT` or `ASSET`. Validation differs per mode and per issue type.
- ASSET items move through `modules/assets/` lifecycle endpoints (assign, transfer, return, incidents, recover, retire), not through general stock transfers. Those endpoints keep the physical location, holder history and stock consistent. `api/README.md` lists the exact asset and issue-type rules.
- Retry-safe creation uses client-supplied keys: `idempotencyKey` for adjustments and store orders, `requestId` for personnel account provisioning. A replay must return the original result, and a changed payload under the same key is rejected.

### Storefront and orders

- The `store_settings` singleton names the one sales warehouse and its farm. Public `/store/*` reads compute availability from that warehouse.
- Back-office store screens show only when the selected farm owns that warehouse (`storeOnly` in `web/shared/config/navigation.ts`).
- Order lifecycle (`modules/store-orders/`): the customer `POST /store/orders` creates a PENDING order.
- On staff confirm, the order allocates stock and creates a DRAFT stock issue. Availability subtracts DRAFT/PENDING_APPROVAL issue lines, so this acts as the reservation. Ship confirms that issue (stock leaves), and cancel cancels it (releases the reservation). Payment (`COD` / `BANK_TRANSFER`) is marked paid manually.
- Money is whole VND carried as strings and handled as `bigint` (`common/money.ts`, `@IsVndAmount`). Quantities are decimal strings with up to 3 decimals, converted to integer thousandths for arithmetic (`store-order.rules.ts`).
- Product images go through `CloudinaryModule` (`src/cloudinary/README.md`).

### Web (`web/`)

- Route groups:
  - `app/(dashboard)` is the back office: `AuthContextProvider` + `AppShell`, protected by Clerk in `proxy.ts`.
  - `app/(store)` is the public storefront with `CartProvider`; the cart lives in the browser and reconciles against verified variants.
  - `app/(auth)` holds the sign-in, sign-up and password-change pages.
- Routes are thin: they compose exports from `features/<capability>/` (`api/`, `components/`, `hooks/`, `types/`). Generic UI, transport and config belong in `shared/`.
- Back-office calls use `useAuthenticatedRequest()` → `shared/api/client.ts` (Axios, with the Clerk token) and pass the selected `farmId`. Public storefront reads use native `fetch`; server-side reads prefer `API_INTERNAL_URL` over `NEXT_PUBLIC_API_URL`.
- After sign-in, everything goes through `/auth/continue` (calls `/auth/me`). A user with any farm role is staff and goes to the back office; everyone else is a customer and goes to the store. Only same-origin destinations are allowed (`features/auth/utils/post-sign-in.ts`).
- Navigation visibility is declarative: `adminOnly` (ADMIN/FARM_OWNER), `staffOnly`, `storeOnly` in `shared/config/navigation.ts`.
- Pure logic is pulled into `*.logic.ts` files with sibling `*.test.mjs` tests.

### Reference data and dashboard

- Suppliers and locations are farm-scoped (ADMIN/FARM_OWNER write). Categories and units have no `farm_id` and are shared by every farm, so their writes require the `ADMIN` role (`@FarmRoles('ADMIN')`; `farmId` only selects the membership being checked). Records are deactivated via `status`, never deleted. A location holding a non-LOST/RETIRED asset cannot change warehouse or be deactivated (409).
- Stock counts reject ASSET items by design; assets are reconciled through asset records. Count/transfer lines for LOT items must carry a `lotId` of the same item.
- `GET /dashboard/summary` computes stock value as on-hand quantity × the item's latest confirmed receipt price (quantity-weighted across that receipt's priced lines; `unit_price` 0 means unpriced) and uses `Asia/Ho_Chi_Minh` for "today".

### Known gaps (marked with `shortcut:` comments)

- The count/transfer lot picker lists only the first 100 balance rows of the warehouse.
- The mobile app cannot create asset transfer requests yet; its asset transfer buttons are hidden.
